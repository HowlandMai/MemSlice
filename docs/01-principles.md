# 01 · 原理

本文讲清一件事：**内存池为什么这样设计**。每个设计点都从"不用它会怎样"出发。

## 1. 为什么要内存池

`malloc`/`free` 是通用分配器，通用意味着它必须处理所有情况：

| 通用分配器的负担 | 具体代价 |
| --- | --- |
| 支持任意尺寸 | 每次分配都要查合适大小的空闲块（分离存储/边界标记/buddy 等） |
| 处理任意释放顺序 | 需要合并相邻空闲块、维护更复杂的元数据 |
| 线程安全 | 加锁或 per-thread 缓存 |
| 元数据开销 | 每个块都要额外的边界标记/尺寸头 |

如果程序的分配模式是**可预测的**——比如大量同尺寸的小对象、频繁申请释放——
那么可以针对性设计，把这些负担去掉。

**内存池换来的收益**：
1. 分配/释放接近 O(1)（只是一个链表操作）
2. 批量向系统申请，摊薄 `malloc` 的调用次数
3. 避免系统分配器为了通用性产生的碎片

**代价**：只对特定尺寸范围有效；超出范围的请求还得回落到 `malloc`。

## 2. 两级分配器

```
        ┌─────────────────────────────┐
请求 →  │  size > kMaxBlockBytes ?    │
        └───────┬─────────────┬───────┘
            是  │             │  否
                ↓             ↓
        ┌───────────────┐  ┌──────────────────────────────┐
        │ 一级分配器     │  │ 二级分配器                    │
        │ 直接 malloc    │  │ 按尺寸分桶 → 空闲链表          │
        │ 直接 free      │  │ 桶空 → 向系统批量申请 chunk    │
        └───────────────┘  └──────────────────────────────┘
```

**为什么大对象不走进池**：假设 8 字节一个桶、最大支持 128 字节，共 16 个桶。
若允许 4KB 请求也走池，就需要为 4KB 建一个桶，而该桶里的块极少被完整利用——
一个 4KB 请求占用 4KB 整块，和直接 `malloc` 没有区别，还多了一层管理开销。

> **设计原则**：池的收益来自"同尺寸反复复用"。尺寸越大、复用越少，收益越趋于零。

## 3. 为什么要自描述头部

先看问题：`free(p)` 只给你一个指针**，没有尺寸**。

经典实现（如 SGI STL）的解法是**要求调用方提供尺寸**：

```cpp
// SGI 风格的接口
pool.deallocate(p, size);   // 调用方必须记得当初申请了多大
```

这很脆弱——调用方记错尺寸就会写坏空闲链表。

**本实现改用自描述头部**：在每个块的用户数据**前面**放一个小头部，记录一切
回收所需的信息。

```
     raw（块的真实起始地址）
      │
      ├──┬──────────────────────┬────────────────────────────┐
      │  │ base (8B)            │ packed (8B)                │  ← 16 字节头部
      │  ├──────────────────────┴────────────────────────────┤
      │  │   （可能的对齐填充）                              │
      └──┤                                                    │
         │            用户数据（用户指针从这里开始）           │
         └────────────────────────────────────────────────────┘
```

`packed` 是一个机器字，用位域压进四样东西：

```
 位:  [ 63 ... 8 ][  7  ][ 6  ][ 5 0 ]
       ↑            ↑      ↑      ↑
       容量         状态   来源   魔数(6位)
```

- **容量**：回收时不需要调用方提供尺寸（本实现与经典实现的关键差异）
- **来源**：区分"池块"与"系统块"，决定回收走哪条路径
- **状态**：标记已分配/已释放，让重复释放能被识别
- **魔数**：识别"这个指针是否属于本池"，用于诊断野指针

代价：每个块多 16 字节。对 8 字节的小对象来说开销明显（200%），但对
64 字节的对象只有 25%。**这是一个明确的取舍**——用内存换接口的健壮性。

## 4. 空闲块复用自身内存（关键约束）

空闲链表需要 `next` 指针。你可以：

- **方案 A**：为每个空闲块额外分配一个节点 —— 浪费内存
- **方案 B**：把 `next` 存在空闲块自己的前 8 字节里 —— 零额外内存 ✓

本实现用方案 B。**但它带来一条必须牢记的约束**：

```
 空闲态:  ┌──────────┬──────────────────────────────┐
          │  next    │   这块内存现在是空闲的        │   ← next 存在块首
          ├──────────┼──────────────────────────────┤
 已分配:  │ base     │  packed  │   用户数据...      │   ← 头部也在块首
          └──────────┴──────────────────────────────┘
          ↑
          同一个地址！
```

> ### ★ 不变量：一个块不可能同时处于「空闲链表态」和「已分配态」
>
> 因为 `next` 与头部**占用同一段内存**。任何在"把块挂回链表之后"还去读写
> 头部的代码，读到的都是链表指针——这是真实的 bug 来源。
>
> 具体的表现与修法见 [03 · 构建日志](03-building-log.md#2-头部与链表指针重叠)。

## 5. 分桶：把 O(n) 变成 O(1)

如果不分桶，所有空闲块一条炼表，那么分配时要**遍历**找一块够大的 —— O(n)。

分桶（segregated storage）的做法：按尺寸分成固定档位，每档一条链表。

```
  请求 1..8 字节    → 桶 0  → [块][块][块]
  请求 9..16 字节   → 桶 1  → [块][块]
  请求 17..24 字节  → 桶 2  → [块]
  ...
  请求 121..128 字节 → 桶 15 → []
```

分配时 `桶号 = (align_up(size) - 1) / kAlignSize`，**直接算出桶号，O(1) 定位**，
再从链表头摘一个即可。

代价是**内部碎片**：请求 9 字节会拿到 16 字节的块，浪费 7 字节。对齐粒度越细，
碎片越少但桶越多。本实现取 8 字节粒度、16 个桶——这是"桶数量"与"碎片率"的折中。

## 6. chunk：批量向系统申请

如果每次分配都 `malloc` 一个小块，那和直接用 `malloc` 没区别。所以桶空时
**一次申请一大块**（chunk），切成很多等长的块挂入链表：

```
  向系统申请一个 chunk（例如 2 * 批量大小 * 块尺寸）
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │ 块 │ 块 │ 块 │ 块 │ 块 │ 块 │ 块 │... │
  └────┴────┴────┴────┴────┴────┴────┴────┘
    ↑ 返回给调用方      ↑ 其余串成链表挂入桶
```

下次同尺寸分配就直接从链表取，**不再触碰系统调用**。

`count` 参数在这里是**入参兼出参**：传入"希望切几个"，返回"实际切了几个"
（因为当前 chunk 的剩余空间可能不够切满）。

> ⚠️ 这里有个坑：`count` 必须初始化为**期望值**而不是 0。曾因初始化为 0 导致
> `count - 1` 下溢、串链写到内存外、段错误。详见
> [03 · 构建日志](03-building-log.md#1-count-必须初始化为期望值)。

## 7. 并发：分桶加锁的取舍

多线程下必须保证正确性。本实现选择**每个桶一把锁**：

```
  桶 0 [锁0]   桶 1 [锁1]   桶 2 [锁2]   ...   桶 15 [锁15]
```

- **优点**：不同尺寸的分配/释放互不阻塞；实现简单，正确性容易论证
- **缺点**：单线程下每次操作都要加解锁——实测这是**主要的性能损失来源**

**为什么不用线程本地缓存（thread-local cache）**：那是真正能消除锁开销的方案
（glibc 的 tcache 就是这么做的），但它引入两个难题：

1. **跨线程归还的所有权问题**：A 线程分配、B 线程释放时，块该回到谁的缓存？
2. **线程退出的回收问题**：线程销毁时，其缓存里的块必须归还，否则泄漏

本项目**刻意不实现**这一层——它是很好的进阶练习，但会让代码复杂度显著上升，
偏离"讲清原理"的目标。相关讨论见 [04 · 性能分析](04-performance-notes.md)。

## 8. 一次分配的完整流程

把上面各点串起来：

```
Allocate(size)
  │
  ├─ 1. 算底层块容量 total = align_up(kHeaderBytes + size, max_align_t)
  │
  ├─ 2. total 在池的范围内？
  │     是 → FreeListPool::Allocate(total)
  │           ├─ 桶号 = (align_up(total) - 1) / kAlignSize
  │           ├─ 加桶锁，从链表头摘一个 → 命中，返回
  │           └─ 链表空 → Refill：向 chunk 要内存（可能触发新 chunk 申请）
  │     否 → malloc(total)
  │
  ├─ 3. 用户指针 p = align_up(raw + kHeaderBytes, max_align_t)
  │
  ├─ 4. 在 p - kHeaderBytes 处写头部：base=raw, packed=容量|来源|已分配|魔数
  │
  └─ 5. 返回 p

Deallocate(p)
  │
  ├─ 1. 从 p - kHeaderBytes 读头部
  │      ★ 顺序关键：先取出 capacity / source / base，
  │        因为第 3 步会把 next 写到块首、覆盖头部
  │
  ├─ 2. source == 池块 → FreeListPool::Deallocate(base, capacity)
  │                     （加桶锁，挂回链表头）
  │     source == 系统块 → free(base)
  │
  └─ 3. 此后不得再触碰头部
```

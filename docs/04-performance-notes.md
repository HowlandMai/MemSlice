# 04 · 性能分析

本文给出**实测数据**与**归因**。结论先行：

> **本池单线程下比 glibc `malloc` 慢约 3.7 倍。差距几乎全部来自加解锁。**
>
> 这不是实现缺陷，而是 [设计权衡](02-design-choices.md#4-并发分桶加锁-vs-无锁-vs-线程本地)
> 的直接后果。本池的价值不在单次分配速度。

## 1. 实测数据

环境：x86-64 / clang / C++20 / glibc / `-O2`，64 个块同时存活，每轮
`free` + `malloc` 交替，20 万次。

运行方式：

```bash
xmake build bench_mempool_lab
./build/linux/x86_64/release/bench_mempool_lab
```

| 配置 | ns/op |
| --- | --- |
| **本池（分桶加锁）** | **13.15** |
| glibc `malloc` / `free` | 3.54 |
| **比值** | **3.71×（更慢）** |

## 2. 归因：差距来自哪里

用一个受控对比把变量分离——同一份代码，只改 `kThreadSafe`：

| 配置 | ns/op | 说明 |
| --- | --- | --- |
| 本池，`kThreadSafe = true` | 19.25 | 每次操作取两次锁（分配一次、释放一次） |
| 本池，`kThreadSafe = false` | **3.68** | 去掉锁，无任何加解锁开销 |
| glibc `malloc` / `free` | 6.71 | 同一批次测量 |
| 裸 `std::mutex` lock + unlock | **7.62** | 无争用下的单次锁成本 |

**读法**：

1. 加锁比去锁慢 `19.25 - 3.68 = 15.57 ns/op`
2. 每次 alloc+free 取两次锁，故单次锁成本约 `15.57 / 2 ≈ 7.8 ns`
3. 这与实测的裸 `mutex` 成本 **7.62 ns** 吻合 ✓

> **结论：差距几乎全部（约 81%）来自锁，而不是空闲链表本身。**
>
> 去掉锁后本池 `3.68` vs glibc `6.71` —— **反而更快**。说明分桶空闲链表这一
> 数据结构是有竞争力的；是线程安全的实现方式带来了代价。

> 注：两次测量的 glibc 数值（3.54 / 6.71）有差异，因为 glibc 的 `tcache` 行为
> 受分配模式影响（是否命中 per-thread 缓存）。**这说明基准数字的意义有限**——
> 这也是本项目不把"池更快"作为卖点的原因之一。

## 3. 指令级归因（可选，用 callgrind）

时间测量给出比值，指令计数能把开销落到具体函数：

```bash
valgrind --tool=callgrind --callgrind-out-file=/tmp/cg.out \
         ./build/linux/x86_64/release/bench_mempool_lab
callgrind_annotate --auto=no /tmp/cg.out | head -20
```

在更早的一个实现上做同样分析时，看到的结果是：`pthread_mutex_lock` 与
`pthread_mutex_unlock` 合计占了**约 47%** 的指令数（每次 alloc+free 配对）。
这从另一个角度印证了第 2 节的结论。

分析方法本身比数字更有价值：**当"为什么慢"说不清时，指令级计数能把猜测变成证据。**

## 4. 为什么 glibc 更快（也是本池慢的根本原因）

glibc 的 `malloc` 有一个 **per-thread cache（tcache）**：

- 每个线程维护自己的小对象缓存，**分配/释放大多数情况不取锁**
- 只有缓存未命中/溢出时才走需要加锁的 arena 路径

也就是说，**glibc 已经实现了本项目刻意没做的"线程本地缓存"**，而且做了二十年，
覆盖了无数边界情况（fork 一致性、`malloc_usable_size`、与 `LD_PRELOAD` 的配合……）。

所以"超过 glibc malloc"这个目标，实际上是要求在一个成熟的工业实现面前，
重新走一遍它的路。**这不是一个学习项目应该追求的目标。**

## 5. 如果要做快，该怎么做（也是不错的进阶练习）

按"收益/复杂度"排序：

| 方案 | 预期收益 | 新增复杂度 | 主要风险 |
| --- | --- | --- | --- |
| **线程本地缓存** | 大（消除热路径的锁） | 高 | **跨线程归还的所有权**；线程退出的回收 |
| 每桶自旋锁 | 中（省去内核态切换） | 低 | 高争用时自旋浪费 CPU |
| 无锁空闲链表（CAS） | 中 | 很高 | ABA 问题；需要 hazard pointer 或 tagged pointer |
| 批量化 API（一次要多个块） | 中 | 低 | 改变接口形态 |

其中 **线程本地缓存**是唯一真正解决问题的方案，但有一个必须设计清楚的难点：

```
线程 A: p = pool.Allocate(64)   → p 进入 A 的本地缓存
线程 B: pool.Deallocate(p)      → 该还回"谁的"链表？
```

- 还回 A 的缓存 → 需要无锁投递队列 + 处理"A 已退出"的窄窗口
- 还回 B 自己的 → **语义错误**：A 的缓存析构时，块可能还在 B 手里
- 还回全局桶 → 退化为加锁路径（但比现在好，因为只有跨线程释放才加锁）

> 我在一个更早的实现上尝试过第三种，两次都没跑通，最终移除了这层。
> 失败过程**也是收获**：它让我理解了"为什么这个问题难"。

## 6. 本池真正可能有优势的场景

单次分配速度不是全部。以下场景本池的设计可能更合适：

| 场景 | 为什么 |
| --- | --- |
| **多线程、分配尺寸分散** | 分桶加锁让不同尺寸互不阻塞 |
| **需要分配延迟可预测** | 无锁路径下分配是纯链表操作，没有 `malloc` 内部的搜索 |
| **长期运行、反复申请释放同尺寸** | 一次 chunk 申请后不再触碰系统调用，碎片可控 |
| **教学/嵌入** | 代码量小（约 500 行核心），可读、可改 |

反之**不适合**：

| 场景 | 原因 |
| --- | --- |
| 单线程高频分配 | 不如直接用 glibc malloc（快 3.7 倍） |
| 大量 1~8 字节小对象 | 16 字节头部开销占比过高（300%） |
| 分配量极少 | 批量申请造成初始浪费 |
| 尺寸差异极大且都走池 | 桶的利用率低 |

## 7. 一句话总结

> 本实现的性能**有意做了取舍**：用单线程速度换实现简洁与正确性易论证。
> 它的教学价值在于展示"每个选择都有代价"，而不是"我造了个更快的分配器"。

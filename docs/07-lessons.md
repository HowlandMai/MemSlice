# 07 · 项目心得：取舍、失败与方法

本文不讲课。它记录的是**做这个项目时实际做的判断、踩的坑、以及改变了什么想法**。

写它的理由：代码能证明"我会写"，而这一篇能说明"我怎么想"——后者更难从代码里看出来。

---

## 一、为什么选"小而完整"而不是"大而全"

最初的动机是"造一个内存池"。但很快遇到一个问题：**内存池的算法没有原创空间了。**
两级分配器、按尺寸分桶、空闲链表复用块内存——SGI STL 在 90 年代就写完了；
glibc 的 `tcache`、jemalloc 的 arena 也比任何个人实现成熟得多。

于是面临一个判断：

```
路线 A：把功能做全（线程本地缓存、mmap 直连、内存整理、可配置策略……）
        → 结果：一个功能齐全但处处不如成熟实现的轮子

路线 B：把规模压小，把一个方向做透
        → 结果：?
```

**我选了 B，并把"做透"的方向定为「可验证性」。**

依据是：如果我要在简历上写"我实现了一个内存池"，面试官会问"它比你读过的
glibc 实现差在哪"。而我如果写"我实现了一个能用不变量审计自证正确性的内存池，
并记录了失败经历"，问题的性质就变了——从"你抄得像不像"变成"你怎么知道它是对的"。

**这个判断后来被验证是对的**：本项目最有价值的部分不是我写的分配算法，
而是 [构建日志](03-building-log.md) 和 [验证方法](05-verification.md)。

> **可迁移的经验**：重造一个成熟组件时，先问"它的正确答案是否已被充分公开"。
> 如果是，那你的价值不在算法，而在**验证深度、边界覆盖、或者诚实的失败记录**。

## 二、连续失败两次之后，我改变了工作顺序

这是本项目最重要的转折点。

### 第一次尝试：线程本地缓存

动机很明确：实测发现单线程性能差距**几乎全部来自锁**（去掉锁后与 `glibc malloc`
相差 0.2%），所以"让分配不走全局锁"是唯一有量级的优化方向。

我以为这不难——教科书上是标准做法。结果连续改了四轮：

```
改 v1 → 段错误
改 v2 → 段错误
改 v3 → 段错误
改 v4 → 段错误
```

每一轮都是同一个模式：**看到症状 → 猜一个原因 → 改一版 → 又崩。**
明明在"修 bug"，却把代码越改越坏。

### 停下来，检查自己的工作方式

四次失败后我做了一件当时觉得"浪费进度"的事：**把改动全部回退**，
然后问自己一个不同的问题——不是"哪里写错了"，而是"**我凭什么认为下一版会更好**"。

答案是：不凭什么。我在猜。

### 第二次尝试：换顺序

于是换了做法——**先建检查手段，再改代码**：

| 步骤 | 做法 | 结果 |
| --- | --- | --- |
| 1 | 先写不变量审计：校验链表无环、节点归属、桶与容量一致、块唯一性 | 得到一个能"自己判断账目对不对"的池 |
| 2 | 把接入拆成两小步：先「只读缓存」（不写入） | 全绿 —— 证明读路径无害 |
| 3 | 再「首次写入缓存」 | 立刻定位：问题就在这一步 |

**第 3 步的失败是有价值的失败**——它精确地告诉了我"哪一步引入了问题"，
而不是像第一次那样"整个改动都崩了，不知道从哪查"。

### 我最终没有做成这件事

**TLS 缓存最终没有实现。** 定位到了失败点（首次写入缓存），但根因没查清，
于是把它整体移除了——**仓库里不留未验证的代码**。

这不是成功故事。但它是一个更真实的故事，也是我在这个项目里学到最多的部分。

> **可迁移的经验**：当同一个问题失败两次以上，问题多半不在代码，而在工作方式。
> **先问"我怎么知道这样改是对的"，再动手。** 检查手段通常不复杂——
> 一次 `fprintf`、一个 `static_assert`、一次受控实验——但它把"猜"变成了"看"。

## 三、几个具体的判断（与代价）

### 自描述头部：用 16 字节换接口安全

每个块在用户数据前放 16 字节头部，记录真实基址、容量、来源、状态、魔数。

**代价**：8 字节对象多付 200% 开销。
**换来的**：`Deallocate(p)` 单参、无需调用方记尺寸、能区分来源、能识别重复释放。

**判断依据**：接口错误是**系统性风险**（调用方传错尺寸会静默写坏堆），
而内存开销是**可度量的**。用可度量的代价换系统性风险的消除，划算。

### 分桶加锁：明知会慢，仍然这么选

**代价**：单线程比 `glibc malloc` 慢约 3 倍。
**换来的**：正确性容易论证、代码量小、无需处理跨线程归还的所有权问题。

**判断依据**：线程本地缓存能把性能提上去，但它引入两个难题——
跨线程释放时块该回谁的缓存、"owner 线程已退出"的窄窗口。
**我两次都没做对**，所以选择不做，并在文档里写清这个取舍。

这不是"最优解"，是"我能论证正确的解"。

### 超对齐：回落而不是统一处理

`alignas(64)` 的类型与"头部紧邻用户指针"的布局冲突（细节见
[06 · STL 分配器](06-allocator.md#4-坑二超对齐类型的布局冲突)）。

**选择**：超对齐请求回落到系统分配，用一个 16 字节前缀记录偏移。
**而不是**：修改所有路径的头部计算来统一支持。

**判断依据**：超对齐类型占比小、通常尺寸大数量少，本就不是池的目标场景。
**为少数情况牺牲常规路径的简洁性是错的。**

## 四、关于"诚实的边界"

这个项目里我最坚持的一件事：**把"做不到"写清楚。**

README 开头就写"比 glibc 慢 3 倍"；`docs/04` 给出完整归因；
`docs/03` 记录失败；TLS 做不成就不留在仓库里。

看起来这是"给自己减分"。但我认为反过来：

- 面试官**一定会问**"为什么不用线程本地缓存"。**提前写上答案**，比被问到才慌乱解释强得多
- "我知道它的边界在哪"本身是一种能力。声称"高性能内存池"却答不出边界，更糟
- 一份诚实的失败记录，比一个勉强能跑的实现更能说明**你是怎么工作的**

> **判断**：简历项目的目标不是"看起来完美"，而是**让面试官相信你讲得清每一个决定**。

## 五、如果重做，我会怎么改

诚实复盘——这几条是如果再来一次会不一样的：

| 方面 | 现在的做法 | 更好的做法 |
| --- | --- | --- |
| **验证时机** | 先写完实现，再补审计和测试 | **不变量应该先写清楚，再写实现**（先想清"什么必须永远成立"） |
| **失败处理** | 同一问题试错 4 次才停下来 | **猜错两次就停**，回头补检查手段 |
| **提交粒度** | 一个大提交塞进全部代码 | 分层提交（骨架 → 审计 → 测试 → 文档），历史本身就是过程证明 |
| **目标设定** | 起初想做"生产级" | 一开始就明确"教学项目"——目标不清会导致过度投入 |

其中前两条是我真正改变了工作习惯的地方。

---

## 六、这个项目最终教会我什么

1. **先建检查手段，再改代码。** 这是最重要的一条，代价是两次失败的尝试
2. **"做不到"要及时说、写清楚。** 挂着不解决的复杂度，比明确的边界更有害
3. **重造轮子时，价值在验证深度而不在算法。** 算法公开了，验证没有
4. **每个选择都要能说出代价。** 说不出代价的选择，多半是没想清楚
5. **失败过程比成功结果更可讲。** 尤其在面试里——它展示的是判断力而非记忆力
